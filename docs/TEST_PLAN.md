# 订单 API 自动化测试计划

版本：1.0　日期：2026-10-15　测试对象：本仓库 `demo_api/server.py`

## 1. 目标与范围

本项目以现有订单演示 API 为被测系统，交付一套可在本机和 GitHub Actions 重复运行、可追溯、可查看失败原因的接口测试。这里的“完整”指**当前四个接口及其已定义业务规则**有成体系的功能、异常、状态变化和响应契约检查，不代表真实电商系统的全部业务能力。

| 接口 | 核心规则 |
| --- | --- |
| `POST /login` | 正确账号密码返回 token；缺少凭据或凭据错误返回相应错误。 |
| `GET /products` | 公开查询商品及库存。 |
| `POST /orders` | 需要有效 Bearer token；成功创建订单并扣减库存；非法请求、未知商品或库存不足不得创建订单。 |
| `GET /orders/{id}` | 需要有效 Bearer token；返回已有订单，未知订单返回 404；读取不改变库存。 |

当前演示服务只有一个商品（ID `101`，初始库存 `5`）、一组练习账号和一个固定 token。支付、取消订单、角色权限、token 过期、并发扣库存和外部数据库均未实现，不纳入本轮验收；如果扩展服务，应先补接口契约与相应测试。

## 2. 当前基线

以提交 `a89c6db` 为基线：pytest 收集到 **27 条用例**，覆盖登录、订单创建与读取、认证拒绝、数量和库存边界、异常 JSON、订单与商品响应的 JSON Schema 校验。`tests/conftest.py` 为每条用例启动独立的本地服务，避免库存和订单互相污染。GitHub Actions 在推送和 Pull Request 时运行测试，并上传 JUnit XML 与 HTML 报告。

本计划先记录现状；下面标为“部分覆盖”或“待补”的内容尚不能算作完整通过的测试项。

## 3. 测试项与优先级

优先级：P0 是核心交易和数据正确性，P1 是主要异常与接口契约，P2 是补充的协议和健壮性检查。

| 编号 | 优先级 | 场景与预期 | 状态 |
| --- | --- | --- | --- |
| AUTH-01 | P0 | 正确凭据登录返回 200 和非空 token。 | 部分覆盖：现有用例只检查 token 为字符串 |
| AUTH-02 | P1 | 分别缺少用户名、密码，以及错误账号或密码时返回规定的 400/401 错误。 | 部分覆盖：缺少用户名未单独验证 |
| AUTH-03 | P1 | 非 JSON 或非对象登录请求返回 400，服务继续可用。 | 待补 |
| PROD-01 | P0 | 商品列表返回 200，符合 `schemas/products.json`。 | 已覆盖 |
| ORD-01 | P0 | 成功创建订单返回 201，可按 ID 查到，库存按数量扣减。 | 已覆盖 |
| ORD-02 | P0 | 库存刚好用完可下单；库存不足返回 409 且库存不变。 | 已覆盖 |
| ORD-03 | P0 | 连续下单按剩余库存判定；连续读取同一订单不改变订单和库存。 | 已覆盖 |
| ORD-04 | P1 | 无 token、错误或空 token 不能创建或读取订单；已有订单内容不泄露。 | 已覆盖 |
| ORD-05 | P1 | 数量为 0、负数、字符串或 null 时返回 400；未知商品返回 404。 | 已覆盖 |
| ORD-06 | P1 | 截断、空、数组或 null 请求体返回 400，库存不变。 | 已覆盖 |
| ORD-07 | P1 | 成功创建的订单符合 `schemas/order.json`；未知订单返回 404。 | 已覆盖 |
| ORD-08 | P1 | 两次成功下单得到不同订单 ID，两个订单都可查询，库存累计扣减。 | 待补 |
| ERR-01 | P1 | 400/401/404/409 的错误响应结构一致，错误码与场景对应。 | 待补 |
| ROUTE-01 | P2 | 未知路径返回 404；响应仍为可解析 JSON。 | 待补 |
| INPUT-01 | P2 | `product_id` 类型、额外字段、Content-Type 的处理符合明确的接口契约。 | 待明确规则后补 |

每条新用例应同时断言 HTTP 状态码和关键响应内容；涉及失败下单时，还应检查库存及订单状态没有意外变化。断言应基于接口契约和测试数据，不依赖用例执行顺序。

## 4. 环境、数据与执行方式

- 本地：Python 3.12、pytest、requests、jsonschema、pytest-html；在项目根目录执行 `python -m pytest -q`。现有 `requirements.txt` 支持 Python 3.10 及以上。
- CI：GitHub Actions 的 Ubuntu + Python 3.12。每次推送和 Pull Request 运行全量用例，失败时也保留报告。
- 数据：每条用例使用独立服务实例，起始商品库存为 5。练习凭据仅用于本地演示，不放入真实环境配置。新增多订单场景要从当前库存推算预期值，不共享硬编码订单 ID。
- 报告：执行 `python -m pytest -q --junitxml=reports/results.xml --html=reports/results.html --self-contained-html`，在 CI 下载 `pytest-results` 查看失败详情；`reports/` 不提交到 Git。
- 冒烟：`python -m pytest -m smoke -v`，覆盖登录及基本下单流程；全量回归仍以不带 `-m` 的命令为准。

## 5. 实施顺序与交付物

1. **冻结当前契约**：整理接口、状态码、错误码和响应字段；确认 `INPUT-01` 中尚无约定的行为，避免把实现细节误写成业务要求。交付接口契约清单。
2. **补齐高价值场景**：先补全 `AUTH-01` 和 `AUTH-02`，再依次实现 `AUTH-03`、`ORD-08`、`ERR-01`，最后补 `ROUTE-01` 和已明确规则的输入场景。交付可独立运行的 pytest 用例与必要的 JSON Schema。
3. **核对质量**：对照第 3 节逐项检查；本地全量运行，并至少连续运行 3 次以发现不稳定用例；检查 CI 结果和报告可下载。发现缺陷时记录对应测试项、复现输入、预期与实际响应、日志、严重程度和修复后的回归结果。
4. **整理交接**：更新 README 的运行、目录、场景和故障排查说明；提交测试计划、用例、契约文件、CI 配置及一份最近一次通过的运行链接。

## 6. 完成标准

- 第 3 节所有 P0、P1 **已定义**场景都有自动化用例并通过；待明确规则的 `INPUT-01` 不以猜测结果充数。
- 每条用例能单独运行；全量套件连续 3 次通过，GitHub Actions 最新运行成功，JUnit XML 和 HTML 报告可获取。
- 没有未记录的 P0/P1 缺陷。已知缺陷需记录复现步骤、影响和处理状态；不能用跳过或放宽断言掩盖失败。
- README 与实际命令、依赖及目录一致，其他人按文档能在干净环境运行。

## 7. 风险与边界

- 当前服务是单进程本地演示实现；本计划中的稳定性检查只能发现测试或本地服务的偶发失败，不能证明生产环境的性能或并发安全。
- GitHub Actions 的公共运行环境可能出现网络安装失败。应区分依赖下载故障与接口断言失败，保留完整日志。
- 真实项目接入时，需另行设计测试环境地址、账号密钥、数据清理、环境隔离和性能目标；本计划不把演示凭据或耗时阈值直接搬到生产环境。
